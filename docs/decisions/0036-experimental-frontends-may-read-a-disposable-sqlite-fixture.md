# 0036: Experimental frontends may read a disposable SQLite fixture

- **Status**: Accepted (2026-11-04)
- **Date**: 2026-11-04

## Context

[ADR 0028](0028-isolated-frontend-experiments.md) keeps frontend experiments on synthetic data and says connecting one to real data needs a separate decision. The GPUI prototype now reads rows, Find, filter and compare through a `ResultSource` trait, so the next useful evidence is how the grid behaves on rows that came from a database: real column types, real NULLs, and a result that is not generated by index.

## Decision

Proposed: an experiment may open one SQLite file that the experiment itself creates, in a temporary directory, from a fixed script with synthetic rows. It may read it through `bookie-core` types and the SQLite driver, read-only, and may not write to it after creation. It must not accept a path from the user or the environment, must not open any other file, must not use stored connections or credentials, must not open a network socket, and must not go around PolicyGuard by any path that a shipped build would use. The experiment's README says the data is synthetic even though it passed through a database.

## Rationale

SQLite needs no server, credentials or network, so the isolation in ADR 0028 holds. A real driver result exercises typed values, NULL handling and spooling without the risk of touching a user's database.

## Alternatives considered

- Stay synthetic only: cheapest, but it cannot show whether the renderer copes with driver-shaped results.
- Allow a user-chosen SQLite file: closer to real use, but it reaches user data, which ADR 0028 forbids without a full architecture and product decision.
- Connect to PostgreSQL in a container: heavier and adds network access.

## Consequences

- A small driver dependency enters the experiment's lockfile and `cargo deny` surface.
- Nothing here approves shipping a second frontend or any access to user databases; that stays a separate decision.
