# 0057: Routine debugger feasibility and the first step

- **Status**: Proposed
- **Date**: 2026-11-19

## Context

Issue [#3099](https://github.com/cozyGarage/BookiE/issues/3099) asks for an SQL routine debugger with breakpoints and requires an ADR before UI work. [ADR 0055](0055-postgresql-routine-debugging-scope.md) (Proposed) already bounds a PL/pgSQL debugger slice. This record does not replace it. It adds what 0055 leaves open: which mechanisms a client can use, which need a server extension, what a read-only or production-safe tool may offer, and the session, capability and layering rules any option must meet. It asks the maintainer to choose between the paths below.

Today BookiE lists routines in the sidebar catalog and opens their source through `Connection::routine_definition`, which `PolicyGuard` wraps as a governed metadata read (`ROUTINE DEFINITION`, `crates/policy/src/guard/governed_routine.rs`). Nothing executes a routine on the user's behalf except ordinary editor SQL.

### What PostgreSQL offers a client

Facts below come from the pgAdmin and pldebugger documentation and the PostgreSQL manual. Items marked "unverified here" were not exercised in a BookiE fixture.

| Mechanism | Server-side requirement | Breakpoints and locals | Licence | Production-safe |
|---|---|---|---|---|
| `pldebugger` (`plugin_debugger`, `pldbgapi`, `pldbg_*` SQL functions; used by pgAdmin and EDB tools) | Library in `shared_preload_libraries` plus a server restart, `CREATE EXTENSION pldbgapi` per database, superuser for pgAdmin-style use. Not part of core PostgreSQL. Availability on managed services is unverified here and must not be assumed. | Yes: breakpoints, step, continue, stack, variables. Two sessions: a target that runs the routine and a proxy that issues `pldbg_*` calls. The target executes real code and may write. | Artistic License 2.0 (upstream README). Used only as a server-side component the administrator installs; BookiE would not link or redistribute it, so it adds no dependency. | No. Executes the routine under a debug hook in a live backend; stepping can stall locks and hold a transaction open. |
| `plpgsql_check` (extension) | `CREATE EXTENSION`; its profiler and tracer need preload. Licence not verified here (believed permissive); check before any reference. | Static analysis of function bodies without running them. No breakpoints. Tracer and profiler exist but need preload. | Verify before use | Static check mode yes; tracer and profiler follow the preload caveat. |
| `RAISE NOTICE` or `RAISE LOG` tracing | None, but the routine source must be edited (DDL) to add the calls. | Output only. No breakpoints; locals appear only where the author printed them. | Core | Notices arrive as `NoticeResponse` messages the driver already drains (`crates/drivers/postgres/src/notices.rs`). Editing a routine is a write. |
| Plain `SELECT`/`CALL` in a `READ ONLY` transaction | None | Runs the routine to completion; PostgreSQL rejects writes with an error. Does not stop volatile side effects that are not transactional (for example calls through `dblink` or `COPY ... PROGRAM` are blocked only if the role lacks the right; outside effects are not covered). | Core | Better than a write, still executes arbitrary routine code. |
| `track_functions`, `pg_stat_user_functions` | Settable per session by a superuser; core | Call counts and time per function. No lines or locals. | Core | Read-only statistics. |
| `pg_stat_statements`, `auto_explain` | Preload, restart | Statement-level statistics or plans, including nested statements. No debugging. | Core contrib modules | Preload needed, so not assumable. |
| `pg_stat_activity`, `pg_blocking_pids` | Core | Which backend runs what, waits and locks. Already the basis of `bookie-pg-sessions`. | Core | Read-only. |
| `GET STACKED DIAGNOSTICS ... PG_CONTEXT` inside a routine's exception block | None | Call stack text at an error, with line numbers. Only for routines that already catch errors. | Core | Read-only observation. |

Conclusion on feasibility: **no core PostgreSQL feature gives a client breakpoints, stepping or local-variable inspection.** Every route to those needs a debugger extension that an administrator preloads and restarts the server for. A client cannot detect that reliably before connecting and cannot install it without server configuration changes. On a read-only or production connection the debugger is both unavailable by default and unsafe, because debugging invokes the routine.

## Decision

1. **Do not start debugger UI, protocol code or driver work.** Neither this record nor 0055 authorises it. Both stay Proposed until the maintainer answers the open questions below.
2. **Recommended first step is the smaller alternative, "observe a routine without a debugger".** It needs no extension: show source and signature (exists), show `pg_stat_user_functions` counters when `track_functions` is on, surface `RAISE` notices and error `CONTEXT`/`PG_CONTEXT` line numbers returned by a normal execution in the editor results area, and optionally offer a `plpgsql_check` static check when the extension is already present. All of it runs through the existing governed execute and metadata paths; it adds no session type and no new operation class beyond the ordinary editor execution a user already performs. A separate issue and ADR decide it; this record only states the direction.
3. **A true debugger, if wanted later, follows 0055 with these additions.** The first engine and mechanism are PostgreSQL PL/pgSQL through `pldebugger`, direct debugging of one selected routine, on an explicitly opted-in development connection. No other engine and no other mechanism is in scope until its own ADR.
4. **Hard security rules for any debugger work:**
   - Human principal only. MCP, `bookie-agentd` and agent principals are denied at the guard, not just hidden in the UI; MCP exposes no debug tool.
   - A connection marked read-only is refused. Debugging is not offered where the saved connection is production unless the maintainer's open question 3 is answered; the default is refused, and the refusal reason is shown.
   - The debug listener and target are never a raw connection. Every command (invoke, set or clear breakpoint, step, continue, abort, variable read) is a guarded operation through `PolicyGuard` ([ADR 0016](0016-governed-consumer-seam.md)): classification, approval where required, durable audit intent, execution, terminal audit outcome. Invoke, step and continue are write-capable and classified as such. Setting a breakpoint and reading state are metadata operations with their own audit target (`routine:schema.name(args)`).
   - No secret or value echo into logs, audit records or error text. Audit stores operation kind, routine identity, outcome, counts and hashes as the existing SQL hash does ([ADR 0038](0038-audit-sql-hash-key.md)), never argument values or locals.
   - Locals are read only through the shared masking path used for result values; when the policy cannot map a local to a masking rule, the value is withheld and shown as unavailable. Variable count, per-value bytes, total response bytes, stack depth, queued events and command time are bounded, and truncation is reported as incomplete state ([ADR 0007](0007-type-and-value-preservation.md) types are preserved, not stringified silently).
   - Production environment rules from the guard apply unchanged: approval is required for write-capable commands, and no environment relaxes them for the debugger.
5. **Cancellation and teardown ([ADR 0005](0005-server-side-cancellation.md)).** The debugger session owns two backends (target and proxy). Both are registered with the session owner ([ADR 0008](0008-connection-and-session-ownership.md)), neither returns to a pool while the debug session lives, and teardown is one sequence: abort the target (`pldbg_abort_target`), ask the server to cancel any running statement on both backends, then end each transaction (rollback) and close the connections, confirming each via `pg_stat_activity` before reporting a terminal state. Close, window shutdown, disconnect, user stop, replacement and transport loss all run that sequence. A target that cannot be confirmed stopped is reported Unknown, never "stopped", and is never replayed. The debugger holds a transaction open by construction; the #1750 lab evidence (`bookie-research`, `evidence/idle-transaction-confirmation-2026-11-19`) shows what a leaked one does on PostgreSQL 17.12: an idle transaction with an assigned xid holds row locks until commit and pins the vacuum horizon for the whole database, and only `idle_in_transaction_session_timeout` (SQLSTATE `25P03`) ends it from the server. So: the debug session sets a short `idle_in_transaction_session_timeout` and `lock_timeout` on both backends where the role may, and the UI warns when it cannot. Each session has a hard total lifetime and per-command timeout. An unconfirmed write outcome enters the reconcile flow of [ADR 0056](0056-audited-reconciliation-of-unknown-write-outcomes.md) instead of a new mechanism.
6. **Capability flag in the driver contract.** `bookie-core` gains one driver-level capability, `routine_debugging`, default false, in the style of `supports_server_cancellation`. A PostgreSQL connection reports it true only after a read-only probe finds the extension installed and visible to the role (`pg_extension` for `pldbgapi`, library loaded), with distinct unavailable reasons: extension missing, library not preloaded, insufficient privilege, read-only connection, not opted in. The probe never installs anything and never runs the routine. Other drivers inherit false and nothing else changes for them.
7. **Crate layout ([ADRs 0018](0018-headless-app-services-crate.md), [0037](0037-results-crate-split.md), [0041](0041-frontends-render-services-decide.md), [0052](0052-gpui-is-the-cross-platform-frontend.md)).** Debugger types (state, event, bounded value) live in `bookie-core` or `bookie-results` only if pure; the `pldbg_*` protocol lives in `crates/drivers/postgres`; the session lifecycle, event stream, generation ids and policy calls live in `bookie-app-services`; `PolicyGuard` stays in `bookie-policy`. GTK and GPUI consume typed events and render them. No debugger protocol, SQL string or raw connection enters `apps/linux` or `apps/gpui`, and `scripts/check-crate-boundaries.py` keeps that true. Late events carry a session generation and are dropped when stale.
8. **MVP scope if option 3 is chosen.** In: source with line markers, line breakpoints, step into/over, continue, stop, bounded stack frames, bounded masked locals read-only. Out: editing variables, evaluating expressions, global breakpoints, attaching to other backends, conditional breakpoints, watchpoints, other engines (MySQL and SQL Server have no equivalent client-reachable mechanism assessed here), automatic extension install or `ALTER SYSTEM`, MCP exposure, and running as a background or unattended job.

## Rationale

A debugger that cannot be offered on the default configuration of PostgreSQL, hosted or self-managed, and that must run user code on the server, is a large safety and support surface for a client whose positioning is read-safe database work. The observe-only path serves the most common need, "what did my routine do and where did it fail", with existing governed paths and no server prerequisites. Keeping the debugger as a gated, later option preserves the security rules above without committing to them now.

## Alternatives considered

- **Build the debugger now (0055 scope) and accept the extension prerequisite.** Deferred, not rejected: feasible only on provisioned development servers; the cost is two-session ownership, write-capable commands and teardown risk for a feature that is unavailable by default.
- **Do not build a debugger; improve `RAISE`/trace output instead.** Recommended as the first step (decision 2). Its limit is that source edits are needed for custom tracing, so BookiE surfaces notices and error context rather than adding them itself.
- **Delegate to external tools (pgAdmin, DBeaver, `psql` with the extension).** Acceptable for users who need breakpoints; zero cost to BookiE, no integration, no policy or audit coverage. Documenting the pointer is part of decision 2.
- **Client-side PL/pgSQL interpreter or instrumenting rewriter that injects `RAISE`.** Rejected: a second execution engine, or silent DDL that changes the user's routine, both unsafe and incomplete.
- **Run the routine in a read-only transaction as a dry run.** Offered only as normal governed execution with a read-only hint; rejected as a "safe debug mode" because non-transactional side effects are not prevented.
- **Attach to an arbitrary running backend.** Rejected: broad authorisation, and the backend belongs to another owner.
- **Debug through MCP for agents.** Rejected: agents must not run write-capable control flow interactively.
- **Auto-install `pldebugger` or edit `shared_preload_libraries`.** Rejected: administrator-owned server change that needs a restart.

## Consequences

- No code changes. Issue #3099 stays open until the maintainer chooses; this record and 0055 both remain Proposed, and accepting one means marking the other Superseded or Deprecated in the same change.
- Required tests for any debugger implementation, written before UI: agent and MCP principals are denied; a read-only connection is refused; every command produces intent and a terminal audit record, including denied, failed, cancelled and timed-out; locals are masked and bounded and truncation is reported; audit and log output contain no argument or local values; teardown on close, disconnect, cancel and panic leaves no backend in `idle in transaction` (checked against `pg_stat_activity`) in a real PostgreSQL fixture with the extension, qualified on a pinned extension and PostgreSQL version; a missing extension, missing preload and missing privilege yield distinct unavailable states; stale events after replacement are dropped; no GTK or GPUI crate depends on the protocol (boundary script).
- Required tests for the observe-only step: notices and `CONTEXT` lines reach the result area, counters absent when `track_functions` is off are shown as unavailable, and no new operation class bypasses `PolicyGuard`.
- The probe, two-session ownership and teardown contracts would become shared contracts and need Policy and Data lane handoffs.

## Open questions for the maintainer

1. Choose: observe-only first (recommended), or the 0055 debugger now, or both in sequence.
2. Must a debugger work on managed PostgreSQL services? If yes it is not feasible (extension and preload are not available to clients there; unverified here per vendor), and the answer is to drop the debugger.
3. Is a debugger ever allowed on a connection tagged production? This record defaults to refuse.
4. Is a server extension prerequisite acceptable as product positioning, given `PRODUCT.md`?
5. Do approvals per step and continue make interactive debugging unusable, and if so is one approval per debug session with per-command audit acceptable?
6. Which lane owns the first slice, and which supported PostgreSQL versions and pinned `pldebugger` release qualify the fixture?
